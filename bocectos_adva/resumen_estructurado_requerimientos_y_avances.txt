====================================================================
1. RESUMEN GENERAL DEL SISTEMA
====================================================================

El sistema academico fue concebido como una plataforma web para gestionar:

- Matricula y pagos
- Materiales y cursos
- Simulacros y resultados
- Asistencia con QR
- Horarios
- Gestion y consulta de estudiantes
- Funciones por roles: administrador, matriculador, docente y estudiante

Vision general registrada en los bocetos:

- Experiencia parecida a una red social en cuanto a uso e interaccion
- Operacion local primero y luego acceso remoto por internet
- Base de datos preparada para nube y crecimiento
- Control por ciclos academicos
- Enfoque fuerte en operacion del matriculador

====================================================================
2. DECISIONES FUNCIONALES Y TECNICAS YA CONSOLIDADAS
====================================================================

Estas decisiones aparecen repetidas o aclaradas a lo largo de los bocetos y del desarrollo:

2.1. Ciclos academicos
- El sistema opera por ciclo activo.
- El administrador puede crear y gestionar ciclos.
- Las operaciones sensibles deben respetar el periodo del ciclo.
- Fuera del rango del ciclo se bloquean matriculas, pagos y cambios operativos.

2.2. Identidad del estudiante
- El DNI es el identificador principal.
- El mismo estudiante no debe duplicarse como usuario por cada ciclo.
- Si el estudiante vuelve en otro ciclo, se reutiliza el mismo usuario y se crea una nueva matricula del ciclo.

2.3. Pagos
- La deuda debe poder consultarse por estudiante y por ciclo.
- El numero de recibo se guarda con autocompletado a 8 digitos.
- Debe existir historial real de pagos.
- El estudiante puede pasar a RETIRED y tambien volver a ACTIVE.

2.4. Importacion masiva
- La academia necesita subir muchos estudiantes desde Excel.
- La carga debe tener preview obligatorio antes de confirmar.
- La importacion debe incluir datos personales, academicos y pagos.

2.5. Carnets
- El carnet academico se genera en PDF.
- Existe plancha A4 para impresion compacta.
- El QR del carnet contiene solo el DNI.

2.6. Despliegue
- Se decidio usar dominio propio.
- El acceso remoto se evaluo con Cloudflare Tunnel.
- La arquitectura prioriza backend y base de datos en la PC de la academia.

4. REQUERIMIENTOS FUNCIONALES CONSOLIDADOS POR MODULO
====================================================================

4.1. Modulo de Matricula

Objetivo:
Registrar estudiantes nuevos y recurrentes, gestionar su inscripcion por ciclo, generar carnets y soportar carga masiva.

Requerimientos consolidados:

- Crear y editar matriculas
- Seleccionar ciclo activo
- Matricular por DNI
- Reutilizar estudiante existente en otros ciclos
- Impedir duplicidad en el mismo ciclo
- Registrar datos personales y academicos
- Manejar datos opcionales: edad, correo, colegio, apoderado, celular del apoderado, foto
- Generar acuerdo de pago y monto inicial
- Gestionar estado del estudiante
- Bloquear operaciones fuera del periodo del ciclo
- Generar plancha A4 de carnets
- Importar estudiantes por Excel con validacion previa

Observaciones de negocio:

- El correo puede repetirse entre ciclos, pero no en el mismo ciclo
- Los datos textuales importantes deben guardarse en mayusculas
- El ciclo cerrado debe bloquear operaciones de matricula

4.2. Modulo de Pagos

Objetivo:
Gestionar deuda, pagos y estado del estudiante dentro del ciclo activo.

Requerimientos consolidados:

- Buscar estudiante por DNI
- Mostrar resumen de deuda
- Registrar pagos
- Guardar numero de recibo con formato de 8 digitos
- Mostrar historial de pagos
- Permitir marcar RETIRED
- Permitir reactivar a ACTIVE
- Permitir pago incluso si el estudiante esta retirado, segun la politica operativa aplicada
- Respetar periodo del ciclo para operaciones mutables

4.3. Modulo de Usuarios

Objetivo:
Consultar estudiantes del ciclo activo con filtros y foco en deuda.

Requerimientos consolidados:

- Tabla solo de estudiantes
- Columnas principales:
  ciclo, modalidad, grupo, DNI, nombres, apellidos, estado, saldo o deuda
- Filtros en tiempo real
- Visualizar quienes faltan pagar
- Exportacion o impresion de listas especificas

4.4. Modulo de Asistencia

Objetivo:
Registrar asistencia por QR y consultar sesiones e historial.

Requerimientos consolidados:

- Escaneo QR
- Lista de presentes y faltaron
- Filtros por modalidad y grupo
- Buscador
- Sonido de confirmacion
- Soporte futuro para tardanzas
- Posible modo de auto-escaneo continuo
- Exportacion de informe de asistencia
- Mejor distribucion por modalidad en sesiones historicas

Observacion futura:
- Envio de mensaje a padre o apoderado despues de asistencia

4.5. Modulo de Simulacros

Objetivo:
Crear eventos de simulacro, validar archivos y procesar resultados.

Requerimientos consolidados:

- Crear evento de simulacro
- Asociar modalidades
- Definir numero de preguntas
- Subir archivo Excel
- Validar codigos de estudiantes antes del procesamiento
- Ingresar clave de respuestas
- Soportar subida de resultados ya procesados
- Gestionar historial de resultados por evento o modalidad
- Soportar parametros tematicos por rango de preguntas

4.6. Modulo de Materiales / Cursos

Objetivo:
Compartir materiales academicos segun modalidad y permisos.

Requerimientos consolidados:

- Crear cursos
- Asignar modalidades con acceso
- Subir PDF, Word, imagenes y otros materiales permitidos
- Previsualizar y descargar archivos
- Editar y borrar curso
- Editar y borrar material
- Subir imagen de portada del curso
- Mostrar materiales con mejor organizacion visual

4.7. Modulo de Horarios

Objetivo:
Publicar horarios por modalidad y grupo.

Requerimientos consolidados:

- Crear horario por modalidad y grupo
- Mostrar a alumnos permitidos
- Usar plantilla semanal
- Exportar o imprimir en PDF

Observacion:
- Este modulo fue identificado como delicado y requiere planificacion detallada.

4.8. Modulo de Resultados / Calificaciones del Estudiante

Objetivo:
Permitir al alumno ver sus resultados de simulacros y evolucion.

Requerimientos consolidados:

- Visualizar resultados personales
- Relacion con simulacros
- Graficos de progreso
- Historial de ultimos simulacros

5. IMPORTACION MASIVA DE MATRICULAS DESDE EXCEL
====================================================================

Necesidad detectada:
- La academia maneja listas manuales en Excel y registrar alumno por alumno es lento.

Flujo consolidado:

1. Subir archivo Excel
2. Hacer preview obligatorio
3. Mostrar filas validas, con error y recurrentes
4. Confirmar importacion

Validaciones clave:

- DNI solo numerico de 8 digitos
- Correo no repetido dentro del mismo ciclo
- Duplicados dentro del archivo
- Modalidad, grupo y turno validos
- Montos correctos
- Recibo numerico con padding a 8 digitos
- Bloqueo si el ciclo esta fuera de periodo

Comportamiento para recurrentes:

- Si el DNI existe y no esta en el ciclo actual, se reutiliza el usuario
- Si ya esta en el ciclo actual, la fila se rechaza

Datos esperados en plantilla:

- dni
- nombres
- apellidos
- correo
- celular
- direccion
- modalidad
- grupo
- turno
- seccion
- edad
- colegio
- apoderado
- celular_apoderado
- monto_total
- monto_inicial
- numero_recibo

7. REQUERIMIENTOS DE INFRAESTRUCTURA Y DESPLIEGUE
====================================================================

Consolidado de decisiones y observaciones:

- El sistema debe poder operar localmente en la academia
- El acceso remoto se evaluo con Cloudflare Tunnel
- Se definio que si o si se gastara en dominio seguro
- El backend y la base de datos se proyectan en la PC de la academia
- Se requiere consolidar el despliegue para una beta estable
- Se deben contemplar respaldos de base de datos y archivos

Puntos tecnicos identificados:

- Punto de entrada unico para frontend y backend
- Persistencia real de PostgreSQL y uploads
- Separacion de entorno desarrollo y produccion
- HTTPS para ciertas funciones como el scanner en celular
- Evaluacion de Docker y WSL2
